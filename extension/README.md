# Inbox Rescue browser extension

A Manifest V3 side panel for desktop Chrome and Edge. Version 0.2 adds Connect Gmail, real scans, explicit restore/undo, and disconnect. The demo remains available while disconnected. No Python process, app server, or AI service is required.

**Status:** local test build. Automated tests simulate Google responses. Live Google authorization, policy acceptance, and mailbox changes still need validation in your browser. This is not a store-published or Google-verified release.

## Install or update

1. Open `chrome://extensions` or `edge://extensions` in a current desktop browser.
2. Enable **Developer mode**.
3. Click **Load unpacked** and select the `extension/` folder containing `manifest.json` (extract ZIPs first). For an existing installation, click **Reload** on its card instead.
4. Close the old Inbox Rescue panel and reopen it from the browser's Extensions menu. Pin the extension for easier access.
5. New identity, storage, and Google API permissions may require browser confirmation.

The side panel can open beside Gmail or another website. It does not read the page or infer which Gmail account that page has open.

## One-time developer OAuth setup (Chrome / Edge)

This step belongs to the project maintainer for a configured release, not every end user. Unpacked builds currently expose it under **Developer setup** so you can test before publishing. Moving the extension folder or loading it into another browser may change its ID and redirect URL.

1. Open the panel's **Developer setup** section. Copy the **Authorized redirect URI** exactly; it is generated by `chrome.identity.getRedirectURL('oauth2')` for this browser installation.
2. In the existing Google Cloud project, enable the **Gmail API**. Under Google Auth Platform, use an External audience in Testing and add the Gmail test account to **Audience → Test users**. Include `https://www.googleapis.com/auth/gmail.modify` under Data Access.
3. Go to **Clients → Create client**, choose **Web application**, and name it `Inbox Rescue Extension`. Add the copied URL under **Authorized redirect URIs**. This redirect flow does not need a JavaScript origin. Do not choose Desktop app and do not reuse its JSON file.
4. Copy only the public **Client ID** ending in `.apps.googleusercontent.com`. Paste it into the panel and click **Save client ID**. Never paste a client secret, access token, or the downloaded JSON.
5. Click **Connect Gmail**, select your test account, and approve the Gmail permission. The panel shows the actual connected email address only after Gmail's profile endpoint succeeds.
6. Click **Check for missed messages**. Verify the displayed account matches the mailbox you intend to manage.

For a configured release, the maintainer can set the public ID in `oauth-config.mjs` and register that release's exact redirect URL. A public ID is not a user credential; do not distribute the Web application's client secret. The browser release and final authorization design must complete the relevant Google verification and store review before broad distribution.

### Authorization design and limits

Edge does not support Chrome's `identity.getAuthToken`; this prototype uses `identity.launchWebAuthFlow` with Google's documented client-side access-token response (`response_type=token`). It validates the exact callback origin/path, random state, expiry, and granted Gmail scope. This is a token flow, not an authorization-code/PKCE flow; no code exchange, client secret, or refresh token is used. Do not treat it as a completed production security review.

Tokens and connected-account details are kept in `chrome.storage.session`, not disk-based `storage.local`. They normally last until expiry or browser-session reset and are cleared by extension reloads. Reconnect when prompted; there is no unattended background refresh. The only configuration stored in `storage.local` is the public client ID. Browsers and the operating system may retain their own login state.

**Disconnect** clears local authorization first, then requests Google token revocation. If revocation cannot be confirmed, remove the app from Google Account connections manually. Disconnecting does not undo previous label changes. Google revocation can affect other grants belonging to the same app project.

### Common setup errors

- `redirect_uri_mismatch`: use the exact URL displayed by this installed extension, including its path, in a Web application client's redirect URI list. Save, wait briefly, and retry.
- Access denied / app in testing: confirm the selected Gmail address is on this project's test-user list. Workspace administrator policies can also block authorization.
- Profile or Gmail request fails: confirm Gmail API is enabled, the right scope is approved, and the account has Gmail.
- Expired or revoked authorization: reconnect. The extension never opens a login prompt automatically on page load.
- Gmail link opens a different account: select the connected account in Gmail before inspecting the message.

## Scan and review

- Checks up to 300 sent messages from the last 90 days, using To/Cc addresses and thread IDs as correspondence evidence.
- Checks up to 100 Spam/Promotions messages from the last 7 days, excluding Trash. Reaching either limit is disclosed.
- Spam and Promotions have separate queues; Spam wins if both labels exist. Counts follow **Show all checked messages** and dismissals.
- No correspondence does not mean unimportant. Header authentication warnings are not cryptographic verification.
- Restore rereads current labels, removes Spam/Promotions, and adds INBOX/Primary only as needed after confirmation.
- Undo reverses only that label delta and refuses obvious conflicts. Restored cards remain in their original review category for undo.
- Undo state and fetched metadata are held only in the current panel. Clearing, rescanning, reloading, disconnecting, or reconnecting removes those undo actions. Changes already applied to Gmail remain. Concurrent updates are not transactional.
- If a network error happens during a label update, the result may be uncertain. Inspect Gmail before retrying. The prototype does not persist an action journal.

## Demo

While disconnected, **Try a demo scan** loads five fictional messages: Spam (2) and Promotions (1) with correspondence evidence, or Spam (3) and Promotions (2) with all messages shown. Restore/undo are simulated. Connect clears demo results and changes the badge to Gmail; disconnect clears real results and returns to Demo.

## Privacy and permissions

`sidePanel` opens the UI, `identity` opens authorization, and `storage` holds the public client ID and session token. Host access and CSP connections are restricted to `gmail.googleapis.com` and `oauth2.googleapis.com`. Google authorization itself opens through the browser identity API. There are no content scripts, page scraping, telemetry, remote scripts, image loading, attachment loading, or third-party AI requests. Subject and sender text is inserted using textContent.

The broad `gmail.modify` scope technically permits sending, but no sending operation is implemented. Metadata responses may include snippets; they are not rendered or deliberately persisted. Browser-session storage and in-memory state are not an OS credential vault.

## Development

No build step. With Node.js 22+, from the repository root:

```sh
node --test extension/tests/*.test.mjs
```

Tests use fake accounts and responses; they do not call Google. Actual browser permissions, OAuth redirects, installation, and Gmail mutations require manual checks.
